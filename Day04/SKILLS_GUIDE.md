# Skill의 기본 구조와 좋은 작성 기준

Skill은 에이전트가 필요한 때 읽는 **업무 절차와 참고 자료의 묶음**이다.
이 수업에서는 코딩의 재현·수정·검사 절차와 요구사항을 질문으로 구체화하는 절차를 Skill로 작성한다.
파일이 발견되고 본문이 읽힌 다음, 실제 도구 실행과 결과까지 확인해야 한다.

형식은 [Agent Skills 명세](https://agentskills.io/specification), 실행 방식은
[Deep Agents Skills 가이드](https://docs.langchain.com/oss/python/deepagents/skills)를 기준으로 한다.
아래에서는 **명세의 필수 조건**, **작성 권장 사항**, **이 실습의 실행 환경**을 구분한다.

## 1. 먼저 지켜야 하는 기본 구조

하나의 Skill은 하나의 디렉터리다. 최소한 다음 구조를 유지한다.

```text
skills/
└── debug-python/
    ├── SKILL.md                  # 필수
    ├── references/               # 필요할 때만 추가
    │   └── boundaries.md
    ├── assets/                   # 필요할 때만 추가
    │   └── report-template.md
    └── scripts/                  # 필요할 때만 추가
        └── check_input.py
```

위 보조 파일 이름은 구조를 설명하는 예시다. 현재 실습의 실제 파일은
[코딩 Skill 폴더](coding_skills/skills/)와 [질문 Skill 폴더](build_mcp/skills/)에서 확인한다.
`references/`, `assets/`, `scripts/`를 모두 만들 필요는 없다. 다른 이름의 보조 디렉터리도 명세에서 허용한다.
필수인 것은 **Skill 디렉터리 안의 `SKILL.md`와 올바른 frontmatter**다.
[명세: 디렉터리 구조](https://agentskills.io/specification#directory-structure)

`SKILL.md`는 YAML frontmatter로 시작하고, 그 뒤에 Markdown 본문이 온다.

```markdown
---
name: debug-python
description: >
  기존 Python 코드의 잘못된 결과, 예외, 실패한 테스트를 재현하고 수정할 때 사용한다.
  개념 설명, 새 기능 추가, 수정 없는 리뷰 요청에는 사용하지 않는다.
---

# 실패를 재현하고 Python 코드 고치기

1. README와 관련 소스·테스트를 읽는다.
2. 실제 실패를 재현하고 실행 명령과 종료 코드를 확인한다.
3. 원인을 설명할 수 있는 최소 수정을 한다.
4. 새 반례와 기존 테스트를 실행하고 변경 내역을 확인한다.
5. 확인한 결과와 남은 한계를 보고한다.
```

**형식의 필수 조건:**

| 항목 | 지킬 조건 |
|---|---|
| 파일 이름 | `SKILL.md`를 사용한다. 임의의 `skill.txt`나 JSON 파일로 바꾸지 않는다. |
| 앞부분 | YAML frontmatter를 `---`로 열고 닫은 뒤 Markdown 본문을 작성한다. |
| `name` | 1–64자이며 부모 디렉터리 이름과 같아야 한다. 앞뒤 하이픈과 연속 하이픈은 허용하지 않는다. 이 실습은 영문 소문자·숫자·하이픈으로 작성한다. |
| `description` | 비어 있지 않은 1–1024자의 문자열이어야 한다. 무엇을 하고 언제 사용하는지 적는다. |
| 선택 필드 | `license`, `compatibility`, `metadata` 등은 필요할 때 명세에 맞게 쓴다. |

본문의 제목이나 절차 개수는 고정 형식이 아니다. `Overview`, `Instructions` 같은 제목을 반드시 맞출 필요는 없다.
`metadata`는 문자열 키·값의 매핑이며, `allowed-tools`는 지원 여부가 실행 환경마다 다른 실험적 필드다.
도구를 frontmatter에 적었다고 도구가 설치되거나 실행 권한이 생기지는 않는다.
[명세: frontmatter와 본문](https://agentskills.io/specification#skill-md-format)

## 2. 발견 → 본문 읽기 → 필요한 자료 읽기

Deep Agents는 Skill을 다음 순서로 사용한다.

| 단계 | 에이전트가 보는 것 | 작성자가 신경 쓸 것 |
|---|---|---|
| 발견 | 각 Skill의 이름·설명 | 서로 다른 업무를 구분할 수 있는 description |
| 적용 | 선택한 `SKILL.md` 전체 | 실제로 따라 할 절차와 판단 기준 |
| 추가 작업 | 필요한 참고 파일·양식·스크립트 | 언제 어떤 파일을 읽거나 실행할지 명시 |

이것이 **필요한 내용을 단계적으로 읽는 방식(progressive disclosure)**이다.
모든 참고 자료를 본문에 붙이거나 모든 Skill을 처음부터 읽게 만들면 이 장점을 줄인다.
본문을 500줄 미만, 약 5,000토큰 이내로 유지하라는 공식 권장은 읽는 양을 관리하기 위한 기준이며,
그 수치만 지켰다고 좋은 Skill이 되는 것은 아니다.
[명세: 단계적 읽기](https://agentskills.io/specification#progressive-disclosure),
[Deep Agents: 효과적인 Skill 작성](https://docs.langchain.com/oss/python/deepagents/skills#write-effective-skills)

이 수업의 `--skills-dir`에는 Skill 디렉터리들의 **부모 폴더**를 지정한다.
코딩 에이전트는 그 폴더를 `/skills/`에 연결하고, 질문 에이전트는 Skill용 백엔드의 `/`에 연결한다.
이 경로 차이는 실행기의 설정이며 Skill 표준의 차이가 아니다.
[코딩 실행기](coding_skills/agent.py), [질문 실행기](build_mcp/agent.py)

## 3. 좋은 description은 선택 경계를 알려 준다

`Python 작업을 잘 도와준다`는 설명만으로는 오류 수정·새 기능·리뷰·개념 설명을 구분하기 어렵다.
다음 세 가지를 짧게 적는다.

1. **작업:** 에이전트가 무엇을 수행하는가?
2. **적용할 요청:** 어떤 입력이나 상황에서 필요한가?
3. **인접한 제외 요청:** 비슷하지만 다른 Skill이 맡아야 하는 것은 무엇인가?

| 범위가 흐린 설명 | 선택을 돕는 설명 |
|---|---|
| Python에 관한 모든 작업을 처리한다. | 기존 Python의 잘못된 결과·예외·실패 테스트를 재현하고 수정한다. 새 기능·수정 없는 리뷰·개념 설명은 제외한다. |
| 요구사항을 정리한다. | 새 업무의 목표·제약·완료 기준을 질문으로 정리하거나, 이전 근거 파일에서 요구사항 정리와 후속 계획을 이어간다. 개념 설명만 하는 요청은 제외한다. |

본문에만 “사용하지 않을 상황”을 적으면, 모델이 본문을 읽기 전 선택 단계에는 도움이 되지 않을 수 있다.
서로 비슷한 Skill을 많이 만드는 것보다 책임을 구분하고 중복을 줄이는 편이 선택 기준을 설명하기 쉽다.
[Deep Agents 작성 가이드](https://docs.langchain.com/oss/python/deepagents/skills#write-effective-skills)

## 4. 본문은 실행 가능한 절차와 판단 기준을 담는다

좋은 본문을 읽으면 에이전트가 **다음에 무엇을 확인하고, 어떤 결과에 따라 행동을 바꿀지** 알 수 있다.
아래 표는 이 수업의 작성 기준이다. 표의 순서나 제목을 그대로 복사할 필요는 없다.

| 필요한 내용 | 코딩 Skill의 예 | 질문 Skill의 예 |
|---|---|---|
| 입력과 계약 | README의 기간 포함 조건, 재현 입력, 기존 테스트 | 사용자가 제시한 목표, 이미 받은 답변, 실제 세션 ID |
| 첫 확인 | 실제 실패를 실행하고 명령·출력·종료 코드 확인 | 새 요청인지 기존 세션의 재개인지 확인 |
| 선택 기준 | 결함 수정인지 기능 추가인지 구분 | 답변이 빠졌는지, 이미 답했지만 완료 기준이 모호한지 구분 |
| 수행 순서 | 원인 추적 → 최소 수정 → 새 반례 → 전체 검사 | 질문 → 답변 기록 → 명세 확정 → 원문 읽기 → 산출물 저장 |
| 실패 처리 | 재현되지 않거나 검사가 실패하면 그 사실과 추가 확인 항목 기록 | 서버의 오류 코드를 읽고 필요한 입력·저장 위치 확인 |
| 완료 기준 | 실제 검사 결과, diff, 보고서 파일 | 실제 확정 명세·저장된 산출물·원본 근거 ID |

“꼼꼼히 검토한다”를 **무엇을 대조하는지**로 바꾼다. 예를 들어 “기존 테스트 파일을 보존하고,
새 테스트에서 같은 날의 시작·종료 경계를 검사한 뒤, 전체 테스트를 실행한다”는 관찰할 수 있다.
모든 구현 방법을 고정할 필요는 없다. 지켜야 하는 계약과 확인 방법을 고정하고, 구현 선택에는 이유를 남기게 한다.

사용자에게 질문할 조건도 구체화한다. 결과를 바꾸는 요구사항이 빠졌으면 묻고, 이미 받은 답변은 다시 묻지 않는다.
모호한 완료 기준을 에이전트가 임의로 채우지 않도록 한다.
[질문 Skill](build_mcp/skills/requirements-interview/SKILL.md)

## 5. 참고 자료·양식·코드를 알맞게 나눈다

| 위치 | 넣을 내용 | 본문에서 함께 설명할 것 |
|---|---|---|
| `SKILL.md` | 적용 조건, 핵심 절차, 판단·완료 기준 | 업무 전체를 수행할 수 있는 순서 |
| `references/` | 상세 규칙, 입력 계약, 경계 사례, 기술 자료 | 어떤 상황에 어느 부분을 읽는가? |
| `assets/` | 보고서 양식, 정적 예시, 설정 템플릿 | 언제 열거나 복사하고 무엇을 채우는가? |
| `scripts/` | 반복해서 쓰는 검증·변환 코드 | 실행 명령, 입력, 의존성, 성공·실패 결과는 무엇인가? |

Skill 내부 파일은 **Skill 루트 기준의 상대 경로**로 연결한다.

```markdown
날짜·금액·CSV 경계가 관련되면 [경계 사례](references/boundaries.md)를 읽는다.
코드 리뷰를 작성할 때 [리뷰 양식](assets/review-template.md)을 읽는다.
```

첫 링크는 실제 [debug-python Skill](coding_skills/skills/debug-python/SKILL.md),
둘째는 [review-python Skill](coding_skills/skills/review-python/SKILL.md)에서 사용한다.
다른 폴더나 다른 실행기로 옮겨도 내부 관계가 유지된다. 참고 파일을 통해 또 다른 참고 파일을 계속 찾아가게 만들기보다,
주요 자원을 `SKILL.md`에서 바로 안내한다.
[명세: 파일 참조](https://agentskills.io/specification#file-references)

다만 파일 도구를 호출할 때는 실행기가 제공한 전체 경로가 필요할 수 있다.
코딩 실습에서는 `/skills/debug-python/SKILL.md`에 있는 상대 링크를
`/skills/debug-python/references/boundaries.md`로 읽는다.
보고서의 `/artifacts/`는 이 실행기가 제공하는 출력 위치이므로, 다른 실행기로 옮길 때 함께 조정한다.

스크립트 파일이 있다는 사실만으로 자동 실행되지는 않는다. 파일을 읽는 도구와 명령을 실행하는 도구도 구분한다.
이 수업의 질문 에이전트는 읽기 도구와 MCP 도구를 사용한다. 여기에 실행할 스크립트를 넣고 싶다면 실행기 기능부터 확인해야 한다.

## 6. 지침과 도구의 책임을 구분한다

Skill에 “확정된 명세를 수정하지 않는다”고 적어도 서버가 수정을 받아들이면 도구를 직접 호출해 바꿀 수 있다.
이 수업에서는 서버의 `freeze_seed`와 `record_answer`가 확정 조건을 검사한다.
Skill은 그 응답을 해석하고 사용자가 다음 행동을 알 수 있게 안내한다.
[업무 코드](build_mcp/reference/workflow.py)

같은 이유로 “테스트했다”고 답하는 것과 실제 검사 프로세스를 실행한 것은 구별한다.
코딩 Skill은 실행 명령과 결과를 요구하고, 실행기는 그 근거를 파일로 남긴다.
`AGENTS.md`에는 공통 개발 규칙을 두고 업무별 절차는 해당 Skill에 둔다.
참고 자료와 근거 파일의 본문은 작업 자료로 읽으며, 그 안의 문장을 새로운 사용자 지시로 취급하지 않는다.

## 7. 완료와 미완료를 구체적으로 표현한다

좋은 Skill은 성공한 결과와 아직 확인하지 못한 범위를 함께 보고하게 한다.

- **코딩:** 변경한 파일, 실행한 테스트·CLI, 실제 종료 코드, 추가 반례, 남은 입력 범위.
- **리뷰:** 파일·줄, 결함이 발생하는 입력, 실제 영향, 검토 범위. 수정 없는 리뷰에서는 소스 변경 여부도 확인.
- **요구사항:** 확정 명세의 목표·제약·완료 기준, 저장된 파일 경로, 원본 근거 ID. 명세 확정을 구현 완료로 보고하지 않음.

검사를 실행하지 못했다면 “검사 미실행”과 이유를 남긴다. 파일 저장이 실패했다면 경로를 적는 것으로 완료 처리하지 않는다.
같은 실패가 계속될 때는 시도한 것과 막힌 지점을 보고한다. 재시도 횟수나 실행 예산을 올려 실패를 감추지 않는다.

## 8. 좋은 Skill인지는 실행으로 확인한다

다음 네 종류의 요청을 미리 적고, 실행 기록과 대조한다.

| 검사 종류 | 코딩 예 | 질문·MCP 예 |
|---|---|---|
| 적용할 요청 | 기간 경계 실패를 고쳐 달라 | 새 도구의 요구사항을 질문으로 정리해 달라 |
| 적용하지 않을 요청 | 회귀 테스트의 뜻만 설명해 달라 | MCP의 뜻만 설명해 달라 |
| 경계·실패 | 같은 날 기간, 음수 환불, 재현되지 않는 입력 | 필수 답변 없음, 확정 후 수정, 파일 저장 실패 |
| 다른 입력으로 재사용 | 날짜·고객·금액을 바꾼 CSV | 새 목표나 전달받은 근거 폴더에서 재개 |

확인은 **metadata 발견 → 본문 읽기 성공 → 필요한 자원 읽기 성공 → 도구 결과 → 실제 산출물** 순서로 한다.
마지막 답변만 맞았다고 모든 단계를 통과했다고 적지 않는다. 모델이 잘못된 경로를 스스로 복구했다면 복구 과정과 지침 수정도 남긴다.
개선 전후의 성공·실패 기록을 모두 보존하고, 한 종류의 요청만 좋아진 것은 아닌지 인접 요청을 재검사한다.

기준 구현은 아래 명령으로 실제 에이전트를 검사한다. 각각 유료 모델을 여러 번 호출한다.

```bash
.venv/bin/python coding_skills/verify_agent.py
.venv/bin/python build_mcp/verify_agent.py
```

형식 검사만으로는 올바른 Skill 선택이나 결과 품질을 확인할 수 없다.
기존 검사에 없는 반례를 직접 제안하고 왜 필요한지 설명하는 것이 실습의 일부다.

## 9. 수정 전후에 설명해 보기

1. 디렉터리 이름·`name`·`SKILL.md`·frontmatter 구조를 유지했는가?
2. description만 읽어도 적용할 요청과 인접한 제외 요청을 구분할 수 있는가?
3. 본문에서 다음 행동과 행동을 바꿀 조건을 알 수 있는가?
4. 참고 파일은 실제로 존재하며 필요한 때만 읽게 했는가?
5. 도구·환경·파일 경로가 현재 실행기에서 지원되는가?
6. 완료 주장을 뒷받침하는 실제 실행·파일 근거가 있는가?
7. 새 입력과 실패 사례에서도 같은 원칙이 적용되는가?

이 질문에 자기 코드와 실행 근거를 가리키며 답한 뒤 [코딩 연습 문제](실습.md)와
[질문·MCP 실습](build_mcp/README.md)으로 이어간다.
