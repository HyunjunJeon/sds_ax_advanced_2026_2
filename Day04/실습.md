# 코딩 Skill 를 개선해보는 연습 문제

[기준 실행](coding_skills/README.md)을 먼저 해본 뒤 진행.
수정 전 [Skill의 기본 구조와 좋은 작성 기준](SKILLS_GUIDE.md)을 읽고, 디렉터리·frontmatter·참고 파일의 관계를 유지한다.
새 작업을 시작할 때 다음처럼 사본을 만든다.
명령은 모두 Day04에서 실행한다. 이미 있는 폴더에는 다시 복사하지 않는다.

```bash
mkdir -p work/my-coding
cp -R coding_skills/skills work/my-coding/skills
.venv/bin/python coding_skills/prepare.py --workspace work/my-coding/project
```

수정한 Skill을 사용할 때는 아래 두 경로를 함께 지정한다.

```bash
.venv/bin/python coding_skills/agent.py --workspace work/my-coding/project --skills-dir work/my-coding/skills --prompt 'CSV 집계의 기간 경계 테스트 실패를 재현하고 수정해 줘. 기존 테스트를 보존하고 새 반례와 실제 검사 결과를 남겨 줘.'
```

각 실행은 유료 모델을 호출한다. 변경은 `work/`에서 하고 실패한 실행의 `evidence/`도 보존한다.
제출에는 요청·관찰·수정 이유·재검사·남은 한계를 적는다. 최종 답변 문장을 똑같이 맞추는 과제가 아니다.

## 1. 발견한 Skill과 사용한 Skill 구분하기

**할 일:** 정상 경로와 `--skills-dir work/my-coding/skills/debug-python`을 비교한다.
각 경로에서 버그 수정 요청과 “회귀 테스트의 뜻만 설명해 줘”를 새 명령으로 실행한다.
시스템 프롬프트나 도구를 바꾸지 않고 발견 경로의 역할을 설명한다.

**확인 기준:** metadata 발견 목록, `SKILL.md` 읽기 요청, 그 읽기의 결과를 각각 제시한다.
에이전트가 다른 방법으로 파일을 찾아 복구했다면 그 과정도 남긴다.

**힌트:** 하네스가 어느 폴더의 하위 디렉터리에서 `SKILL.md`를 찾는지 실제 구조와 대조한다.

**정리:** “파일이 존재한다”와 “Skill로 발견됐다”는 어떻게 다른가?

## 2. 선택 조건을 바꾸고 인접 요청으로 검사하기

**할 일:** `debug-python` 사본의 description을 “Python 관련 모든 질문에 사용한다”로 바꿔 본다.
아래 요청에서 어떤 본문을 읽는지 관찰하고, 필요한 작업에 선택되도록 description을 고친다.

- `회귀 테스트가 무엇인지 설명해 줘. 프로젝트 작업은 아니야.`
- `기간 경계 테스트가 실패해. 원인을 재현하고 고쳐 줘.`
- `코드를 수정하지 말고 결함을 리뷰해 줘.`
- `CLI에 고객 필터를 추가해 줘. 옵션 이름과 동작은 먼저 정하자.`

**확인 기준:** 같은 단어가 등장한다는 이유만으로 같은 Skill을 고르지 않는다.
description을 고친 뒤 개념 설명과 실제 수정 요청을 모두 다시 검사한다.
모델이 처음부터 잘 구분했다면 “이번 실행에서 선택 차이는 관찰하지 못했다”고 기록한다.

**정리:** 본문을 읽기 전의 선택에 영향을 주려면 어느 부분을 고쳐야 하는가?

## 3. 참고 파일 경로와 보고서 절차 고치기

**할 일:** 리뷰 Skill 사본의 양식 링크를 `assets/missing.md`로 바꾼다.
리뷰를 요청하고 실제 읽기 결과를 확인한 뒤 올바른 자원 경로로 고친다.
양식 전체를 system prompt나 Skill 본문에 붙여 넣지 않는다.

**확인 기준:** Skill 읽기·양식 읽기·리뷰 파일 생성을 각각 확인한다.
모델이 경로를 스스로 복구했어도 원본 지침의 잘못된 경로를 고친다.
리뷰가 지적한 결함에는 코드 위치·발생 입력·영향이 있어야 한다.

**정리:** 본문, 참고 자료, 결과 양식을 파일로 나눈 이유를 설명한다.

## 4. 재현과 최소 수정, 새 반례를 연결하기

**할 일:** 새 프로젝트 사본에서 실패를 직접 읽고, 예상 원인을 자기 말로 쓴 뒤 수정 Skill을 실행한다.
시작일과 종료일이 같은 경우, 종료일의 음수 환불, 기간 바로 밖 거래 중 새 반례 두 개를 고른다.
기존 `tests/test_report.py`는 보존하고 추가 검사는 새 파일에 둔다.

**확인 기준:** 수정 전 실제 실패, 수정 후 실제 전체 검사, 새 반례의 검사 결과와 diff가 있다.
기대값을 구현에 넣거나 기존 테스트를 삭제·skip/xfail 처리해서 통과시키지 않는다.

**추가 도전:** 날짜·고객·금액을 모두 바꾼 입력에도 같은 수정이 적용되는지 확인한다.

**정리:** 기존 실패 하나를 없앤 것과 경계 조건을 이해한 것은 어떤 근거로 구별하는가?

## 5. 같은 프로젝트에서 리뷰와 기능 추가 구분하기

**할 일:** 수정한 프로젝트를 먼저 “수정 없는 리뷰”로 실행한다.
이어서 `--customer` 기능을 요청한다. 정확한 이름 일치, 미지정 시 기존 결과, 없는 고객의 빈 결과를 계약에 포함한다.
기능 추가 전 새 테스트가 실패하고, 구현 뒤 기존·새 테스트가 모두 통과하는지 확인한다.

**확인 기준:** 리뷰 실행의 `changes.patch`는 비어 있고 리뷰 파일은 존재한다.
기능 추가 실행에서는 소스·새 테스트·README 변경과 직접 호출한 CLI 결과가 있다.
미지정·알려진 고객·없는 고객·이름 일부만 같은 고객을 각각 확인한다.

**정리:** “리뷰해 줘”와 “고쳐 줘”의 차이를 description·본문·결과에서 각각 설명한다.

## 6. 새 코딩 업무의 Skill을 직접 만들기

**할 일:** `work/my-coding/skills/` 아래 새 Skill을 작성한다. 예를 들어 문서와 CLI 도움말 대조,
입력 검증 보강, 동작을 보존하는 작은 리팩터링 중 하나를 고른다.
먼저 적용할 요청과 제외할 요청, 필요한 입력, 실제 완료 검사 방법을 적는다.

**확인 기준:** 이름과 description만 바꾼 복제에 그치지 않고 업무에 맞는 절차와 검사를 제시한다.
새 Skill이 필요한 요청과 불필요한 요청을 각각 실행하고, 날짜·금액·입력 파일 중 하나를 바꾼 사례에도 적용한다.
실패한 실행과 미확인 범위를 포함해 결과를 설명한다.

**마지막 설명:** 다른 작은 Python 프로젝트로 옮길 때 유지할 규칙과 바꿔야 할 프로젝트 계약을 구분한다.
질문은 수업 Discord에 현재 단계·기대한 결과·실제 결과·근거 경로를 남긴다.

여기까지 마쳤으면 [질문 강화형 Deep Agent와 MCP 서버 만들기](build_mcp/README.md)로 이어간다.
코딩 도구를 직접 사용했던 에이전트와 MCP 서버의 도구를 호출하는 에이전트를 비교한다.

## 선택 참고: 다른 Skill과 비교하기

[skills.sh](https://skills.sh/)와 [SkillsMP](https://skillsmp.com/)에서 개발 업무를 검색하고,
후보의 원본 저장소에서 `SKILL.md`와 보조 파일을 읽는다.
공식 예제는 [Anthropic Skills](https://github.com/anthropics/skills),
[OpenAI Plugins](https://github.com/openai/plugins),
[Vercel Agent Skills](https://github.com/vercel-labs/agent-skills)를 참고할 수 있다.
가져오고 싶은 절차 한 가지를 고르고, 자신의 프로젝트에서 검증할 요청·반례를 함께 적는다.
