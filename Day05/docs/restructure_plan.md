## 1. 수업의 목표와 중심 사례

수강생이 수업을 마치면 다음을 실행 근거로 설명할 수 있어야 한다.

1. 업무 정책을 기대 상태·금지 행동·허용되는 복구·응답 기준으로 바꾼다.
2. 에이전트의 완료 주장과 서비스의 실제 상태를 구분한다.
3. Trace에서 관찰 사실과 원인 가설을 나눠 기록한다.
4. 평가기에 정상·실패·근거 누락 반례를 넣어 신뢰할 수 있는지 확인한다.
5. 한 조건을 수정하고 같은 기준에서 개선·회귀·평가 불능을 설명한다.

모든 단계는 **주문 취소·결제 환불·예약 재고 복원**을 사용한다. CS 담당자의 요청, 결제 정책,
서비스 오류, 주문 상태, 고객 안내를 같은 사건으로 이어서 읽는다. 실제 결제 서비스 연결은 수업 목표에 포함하지 않는다.
기존 모의 업무 환경과 정책을 활용한다. 현재 서비스별 커밋과 장애 주입의 범위는
`Day05/business_lab/data/order_policy.md:42`에 명시되어 있다.

강사가 제공할 것은 업무 서비스·초기 상태·실행 기반·작은 정상 예시다. 수강생이 만들 것은
추가 Scenario, 검수 근거, 최소 한 항목의 평가 코드와 반례, Evidence Card, 개선 가설과 비교 보고서다.
수강생의 실습 기록을 실제 현업 담당자의 승인으로 표기하지 않는다.

## 2. 번호 실습과 결과물 연결

다음은 새 번호 체계의 제안이다. 기존 파일명은 이 계획 단계에서 바꾸지 않는다.
각 실행 진입점에는 입력 확인 → 핵심 처리 → 결과 저장이 보이게 하고, 업무 판단이 숨겨진
단일 실행 함수만 호출하는 구성은 줄인다. 재사용 함수의 계약과 필요한 코드 위치를 함께 안내한다.

| 새 단계 | 발표 자료와의 연결 | 수강생이 하는 일 | 다음 단계로 넘길 결과물 | 시간 |
|---|---|---|---|---:|
| 00 준비 | 1~5: 평가의 대상 | 실제 완료·정책 준수·응답 품질을 구분하고 연결을 점검한다 | 실행 환경 확인, 평가할 업무 범위 | 20분 |
| 01 업무 기준과 Scenario 초안 | 7~19: 인터뷰·문서·Trace, 최소 쌍, 커버리지 | 강사가 제공한 업무 담당자 인터뷰 예시·정책·운영 사건에서 기준을 추출하고 경계 사례를 추가한다 | 근거가 연결된 Scenario 초안, 커버리지 표 | 50분 |

| 07 한 조건 수정과 비교 | 49~58: 같은 Item·반복·회귀·불확실성 | Evidence Card에 근거해 candidate를 만들고 같은 조건으로 실행·재평가한다 | 두 버전의 비교, 조건별 결과, 비용·시간의 관측 범위 | 45분 |

01에서 정책과 대표 정상 사례를 함께 완성하고, 수강생은 최소 한 개의 경계 사례를 추가한다.
08에서 승격한 사례는 현재 비교의 동결 데이터에 끼워 넣지 않는다. 새 버전으로 검수한 후
baseline과 candidate 모두를 다시 평가하는 다음 실험에 사용한다.

실습 결과는 `outputs/` 아래 실행별로 보관한다. 초안, 승인 데이터, 실행 원자료, 평가 판정,
사람 검수, 개선 보고서를 구분하고 원자료를 덮어쓰지 않는 이름·참조 규칙을 마련한다.
각 단계는 필요한 이전 결과물의 ID·버전을 확인한다. 없는 결과물이나 보류 상태를 임의로 생성해 넘기지 않는다.

## 3. 수업 흐름을 위해 필요한 변경

### 골든 작성과 검수의 실제 연결

현재 로더는 승인된 JSON을 읽는 구조다(`Day05/business_lab/dataset.py:18`).
기존 엑셀 회수는 DeepEval의 질문·기대 답변으로 연결된다(`Day05/05_review_roundtrip.py:33`).
이를 주문 취소 Scenario 계약으로 연결한다.

- 인터뷰 예시, 정책 원문, 비식별화한 교육용 사건 기록을 시작 자료로 제공한다.
- 원문 식별자·절·정책 버전·검수 사유를 Scenario에 남긴다. Trace 출처라면 초기 상태 복원과 비식별화 기록도 남긴다.
- 초안과 검수 완료 데이터를 분리한다. 검수자의 판단과 이름은 사람이 입력한다.
- 상태만 승인이고 기준·근거가 비어 있는 경우를 차단한다. 같은 사건에서 파생한 사례는 family 단위로 분할한다.
- 문서 기반 합성은 초안 생성의 보조 경로로 둔다. 사람이 직접 만든 초안도 같은 검수 경로를 거친다.
- 순서·대상·보호 상태 규칙을 Scenario에서 확인할 수 있게 보강한다. 임의 코드 실행을 허용하는 범용 규칙 엔진으로 확장하지 않는다.

### 실제 실행, 채점, 개선을 분리

현재 `experiment.run()`은 실행과 채점을 함께 수행한다(`Day05/business_lab/experiment.py:81`).
또한 candidate의 개선 지침이 미리 정의되어 있다(`Day05/business_lab/agents.py:27`).

- 실행 단계는 초기 상태·서비스 사건·응답·오류·사용량·모델 및 코드 버전을 수집한다.
- 채점 단계는 저장된 원자료를 읽는다. 평가기나 rubric을 수정할 때 Agent를 불필요하게 재실행하지 않는다.
- baseline을 먼저 실행하고 분석한다. 수강생은 가설과 재평가 기준을 쓴 뒤 candidate를 만든다.
- 강사용 비교 예시는 별도로 보존한다. 수강생에게는 baseline과 자신의 변경을 기록할 진입점을 제공한다.
- 두 버전 비교 시 같은 데이터·fixture·모델·도구·예산을 확인한다. Agent 변경 부분은 별도의 버전 차이로 기록한다.
- 평가 기준을 변경했다면 두 버전의 원자료를 새 평가기·Judge 설정으로 모두 재채점한다.
- Langfuse Dataset item·Run·Trace·Observation 연결을 실행 단계에서 보존하고, 이후 판정을 같은 실행에 연결한다.

### 최소한의 여러 턴 실습

현재는 요청 한 건으로 Agent를 호출한다(`Day05/business_lab/agents.py:124`).
한 개의 필수 Episode를 추가한다: **주문 번호 없는 취소 요청 → 확인 질문 → 주문 번호 제공 → 처리·상태 확인**.

- 첫 턴은 적절한 질문 여부와 쓰기 없음으로 평가한다. Episode 성공은 최종 종료 조건으로 따로 평가한다.
- 동일 Episode 안에서는 대화 맥락과 업무 상태를 유지한다. 새로운 반복 실행에서는 둘 다 초기화한다.
- 사용자 후속 응답은 사전에 정한 규칙으로 제공한다. 사용자 시뮬레이터가 평가 정답이나 개선 힌트를 알려주지 않는다.
- 최대 턴·종료 조건·모델 및 도구 호출 예산은 Episode 전체에 적용한다. 턴마다 예산을 초기화하지 않는다.
- session_id·episode_id·turn_index를 연결하고 턴별 Trace를 보관한다.
- 잘못된 대상 정정·승인 범위 변경은 확장 실습으로 둔다.

### Trace 분석과 평가기 교육

현재 서비스 이벤트에는 인자·결과·시각·Observation ID가 있다(`Day05/business_lab/contracts.py:57`).
정책 평가기는 순차 이벤트에서 대상과 선행 조건을 검사한다(`Day05/business_lab/evaluators.py:81`).

- 모델의 Tool 호출 ID, 서비스 실행, Observation의 부모 관계를 연결한다. 중복된 계측 스팬을 호출 두 번으로 세지 않는다.
- 화면에서 관측한 사실과 평가기가 실제 받은 근거를 대조한다. 페이지·하위 Observation 누락을 검출한다.
- 병렬 조회의 시간순 나열만으로 의존 관계를 단정하지 않는다. 병렬 사례는 작은 제공 기록으로 읽고, 코드의 지원 범위를 명시한다.
- Evidence Card에는 관찰 사실·위반 기준·원인 가설·대안 가설·변경 한 가지·검증 계획을 별도 칸으로 둔다.
- 핵심 지표는 실제 상태, 보호 상태, 대상·권한·순서, 복구·중복, 응답 품질이다.
- 수강생은 한 항목의 입력·판정 계약과 반례를 먼저 정한 뒤 평가 코드를 작성하거나 보강한다. 업무 서비스와 전체 평가 프레임워크 구현은 강사가 제공한다.
- Tool 이름 집합 지표가 같은데 결과가 다른 작은 반례도 제공한다. 이름 일치를 전체 과정의 정답으로 사용하지 않는다.
- 사람은 Judge의 점수·이유를 먼저 보지 않고 같은 객체·같은 rubric으로 판정한다.
- Judge 보정에 쓴 사례와 최종 확인 사례를 분리한다. 수정한 rubric은 별도 버전으로 기록한다.

### 비교와 승인·보류

현재 반복 분모·오류 구분·비교·bootstrap은 재사용할 수 있다(`Day05/business_lab/reporting.py:38`).
실제 실행 비용은 아직 미확인이다(`Day05/README.md:138`).

- 예정 실행 수를 먼저 고정하고, 오류·미채점·누락은 분모와 상태 표에 남긴다.
- 평균 통과율 차이와 모든 반복을 통과한 사례의 변화 표를 따로 제공한다.
- 같은 시나리오의 반복을 독립 업무 사례 수로 세지 않는다. 표본이 작으면 불확실성을 명시한다.
- 품질·정책·회귀·유효 평가·자원 예산·holdout 확인의 판단 기준을 실행 전에 기록한다.
- Agent 비용과 Judge 비용을 구분한다. 비용 정보를 확보할 수 없으면 미확인으로 남기고, 비용 기준 충족이라고 보고하지 않는다.
- 실패가 없는 경우에도 특정 수정이 개선을 만들었다고 단정하지 않는다. 추가 가설·사례가 필요한 상태로 보고한다.

현재 프로젝트는 설치 패키지 모드가 아니다(`Day05/pyproject.toml:25`). 따라서 기존 번호 파일을
하위 폴더로 옮기기만 하면 실행 위치에 따른 import 문제가 생길 수 있다. 이동 전에 Day05에서의
실행 방식을 정하고, import·상대 경로·문서 링크를 함께 검증한다. 새 폴더 배치만을 위한 패키지 확장은 피한다.

## 5. 구현 순서와 완료 기준

한 단계의 결과물이 다음 단계에서 실제로 사용되는지부터 확인한다.

| 구현 묶음 | 범위 | 완료 기준 |
|---|---|---|
| A. Scenario 작성·검수 | 자료·계약·초안·검수·동결 | 수강생이 추가한 사례가 검수 후 실제 실행 대상으로 들어가고, 미검수·빈 기준·family 분할 오류는 차단된다. |
| B. 실행과 근거 | 기록/채점 분리·Langfuse·Episode | 1턴 질문과 2턴 업무 완료를 구분하며, 반복은 초기화되고 중단된 실행의 부분 상태도 보존된다. |
| C. 평가와 진단 | Evidence Card·평가기 반례·Judge 검수 | 잘못된 대상·차단된 쓰기·중복·근거 누락을 구분하고, 사람 판정과 Judge의 불일치를 추적한다. |
| D. 개선과 수업 통합 | candidate·동일 조건 비교·회귀 승격·번호/문서 재편 | 새 수강생 환경에서 00~09를 순서대로 진행하여 하나의 근거 연결이 완성된다. |

검증은 기존 테스트 보존, 의미 있는 신규 계약·반례 테스트, 한정된 실제 모델·Langfuse 연결,
수업 순서의 전체 리허설로 나눈다. 실제 API 실행 직전에는 횟수 규모와 외부 기록 대상을 알린다.
계약 테스트 통과를 LLM 성능 향상으로 설명하지 않는다.

수업 완료의 기준은 실행 성공만이 아니다. 수강생이 검수한 사례 한 개, 관찰 사실과 가설을
분리한 Evidence Card 한 개, 직접 작성·보강한 평가 코드와 반례 한 개, 개선 또는 보류를 설명하는 비교 보고서를 남겨야 한다.

## 6. 시간과 실행 규모 조정

- 6시간: 위 핵심 과정과 최소 2턴 Episode를 진행한다. 자료 읽기·초안·검수는 대표 사례 중심으로 한다.
- 8시간: 도구 응답 계약 오류, 사용자 대상 정정, Judge 보정 후 별도 확인, holdout 분석에 시간을 더 배정한다.
- 3~4시간: 강사가 준비한 검수 자료·실제 실행 기록을 활용한다. Trace 분석·평가기 반례·작은 개선 실험에 집중하며, 골든 확보와 전체 평가를 모두 직접 했다고 설명하지 않는다.

실제 실행은 팀별로 사전 선택한 시나리오 N × 반복 K × 버전 2를 기본 계산으로 삼는다.
예를 들어 N=3, K=2면 12시도다. 현재 단일 요청 호출 한도 기준으로 Agent 최대 약 144회,
Judge는 재시도를 제외하고 대략 12~36회 규모이며 이는 전체 업무 커버리지 검증이 아닌 선택 문항 실험이다
(`Day05/business_lab/agents.py:10`, `Day05/business_lab/experiment.py:94`).
여러 턴 도입 시에는 Episode 전체 예산을 고정한 뒤 다시 산정한다.

전체 시나리오 비교용으로는 버전과 원자료가 보존된 강사 실행 기록을 준비한다. 실시간 실행 결과와
조건이 다른 기록을 합쳐 하나의 개선율로 만들지 않는다. 외부 API 지연에 대비해 실제 기록 분석을
계속할 수 있게 준비하되, 재채점과 새 실행을 결과에서 구분한다.

최종 시간 배분은 총 수업 시간과 수강생의 Langfuse 사용 경험을 확인한 뒤 조정한다.
