# Day02 고급 구현 과제

**목표:** 문서 근거 RAG의 검색 합류, 인용 검증, 시점·버전 선택, 표 근거 보존, 갱신 일관성의 실패를 코드로 해결하고, 개선 효과를 통제 실험으로 설명한다.

00~06은 읽고 실행할 완성 예제다. **07(검색 합류)·08(인용 검증)와 10~12 알고리즘을 직접 구현한다.** 구현 위치는 `student_tasks.py`의 `NotImplementedError`이고, 함수의 공개 계약은 코드 docstring에 정의되어 있다. 최종 제출은 **자신의 구현을 실제 검색·검증 경로에 연결한 통합 변경**이다. 모델 변경, 정답 하드코딩, 테스트 삭제, 범위·예산 우회로 실패를 숨기는 방식은 인정하지 않는다.

모든 과제 파일은 실행 자체가 테스트다. 예: `uv run python 10_version_challenge.py`를 실행하면 안내문과 함께 해당 과제의 공개 테스트가 돌아간다. 구현 전 실패가 정상이다.

## A. 시점·버전 유효 문서 선택 — 25점

**실패 상황:** 질의의 as_of가 2026-06-30에서 07-01로 지나면 유효 SLA가 v1에서 v2로 바뀌어야 하는데, 검색 점수가 높은 만료 v1이 그대로 답변 근거로 남는다. draft 개정안도 미래 유효일과 무관하게 근거가 되어서는 안 된다.

진입 파일: [10_version_challenge.py](10_version_challenge.py). 구현 함수: `student_tasks.effective_documents`. 연결 위치: 검색 전 단계의 후보 확정(`RetrievalContext`가 읽는 manifest/catalog 범위)과 `day02 ask --as-of` 실행.

요구사항:

1. 제외 이유는 고객 → 상태 → 미래 → 만료 순서로 한 문서당 하나만 붙는다. 유효 기간은 반개구간 `[valid_from, valid_until)`이다.
2. 같은 (family, title)에서 유효 구간이 겹치는 catalog 오류는 최신 `valid_from` 문서로 해소하고, 밀려난 문서에 `superseded` 이유를 남긴다.
3. 결과 정렬은 결정적이어야 한다(documents는 title·uri, excluded는 uri).
4. `data/business/catalog.json` 전체에 as_of 6/30, 7/1, 7/15, 9/8을 적용해 집합 변화를 기록한다.
5. 실제 질의와 연결한다. `day02 ask "알파 SLA 신청 기한"`이 `--as-of 2026-07-15`에서 15일, `--as-of 2026-09-08`에서 20일(추가 약정)을 답하는지 대조한다. 집합과 답변이 함께 바뀌어야 한다.

필수 검증:

```bash
uv run python 10_version_challenge.py
```

추가로 학생이 최소 세 반례를 작성한다: 경계일 당일/다음날, 유효 기간이 겹치는 두 approved 문서, 미래 유효일인 draft. 각 반례가 실제 코퍼스의 어떤 오류 상황을 모사하는지 설명한다.

배점: 이유 판정·경계 계약 10, 실제 질의 연결과 15일/20일 대조 8, 추가 반례·집합 변화 설명 7.

## B. 표 근거 보존 선택 — 25점

**실패 상황:** 작은 근거 예산에서 관련도 순서로만 표 조각을 고르면 단위 행과 각주가 잘리고, "20%"처럼 적용 조건 없는 수치가 근거로 남는다.

진입 파일: [11_table_challenge.py](11_table_challenge.py). 구현 함수: `student_tasks.select_table_evidence`(비용 함수 `render_table_context`는 공개된 것을 그대로 쓴다). 연결 위치: `src/day02/tools/tables.py`의 표 파싱과 근거 카드 바이트 예산.

요구사항:

1. 목적함수는 (1) required 커버 최대화, (2) 렌더링 바이트 최소화, (3) ID 사전순 최소화다. 완전 커버가 불가능하면 예산 내 최선의 부분해를 반환한다.
2. 선택된 모든 블록의 `requires`가 함께 선택되어야 한다. 의존성은 전이적이다. 예산이 묶음보다 1바이트 작으면 묶음 전체가 배제된다.
3. 한글 UTF-8과 ID/개행 렌더링 비용까지 포함한다. 비용 함수를 피하기 위해 원문을 자르거나 ID를 지우지 않는다.
4. `sla-a-v2.md`를 `markdown_tables`로 파싱해 헤더·데이터·각주 블록과 `covers`/`requires` 관계를 구성한다. 이 관계의 추출 근거를 설명하고, 공개 테스트가 그 의미상 정확성까지 보증하지 않는다고 명시한다.
5. 실제 검색 결과와 연결한다. 근거 예산(기본 24,000바이트)의 1/10 수준에서 관련도 상위 순서와 선택 결과를 비교하고, `--format table-analysis` 답변의 인용이 단위와 함께 남았는지 대조한다.

필수 검증:

```bash
uv run python 11_table_challenge.py
```

추가로 학생이 최소 세 반례를 작성한다: 커버가 겹치는 유사 조각 묶음, 예산이 묶음보다 1바이트 작은 경우, 의존성이 전이되는 세 층 이상 구조.

배점: 선택 계약·공개 반례 10, 실제 표 연결과 단위 보존 대조 8, 추가 반례·비용 분석 7.

## C. 문서 갱신과 세션 일관성 — 30점

**실패 상황:** 턴 1이 v2 원문 해시로 인용해 답했다. 턴 사이에 문서가 재적재되었지만 세션은 대화만 기억하므로, 턴 2의 후속 답변이 낡은 근거 위에 서 있어도 아무도 알아채지 못한다.

진입 파일: [12_refresh_challenge.py](12_refresh_challenge.py). 구현 대상: `student_tasks.SessionLedger`. 연결 위치: `05_multiturn.py`의 세션 실행과 `outputs/manifests`의 remote_hash.

요구사항:

1. SQLite에 턴별 (evidence_id, uri, content_hash)을 영속화한다. Python 전역 변수나 메모리 dict로 해결하지 않는다.
2. 턴 번호는 세션·스코프 안에서 단조 증가하며 재오픈 후에도 이어진다. 스코프(고객·기준일·namespace)가 다른 턴은 같은 session 이름이어도 격리된다.
3. `stale_evidence`는 현재 해시와 다른 인용뿐 아니라, 원문을 더 이상 확인할 수 없는 인용도 보수적으로 stale로 보고한다. 결과는 (turn, evidence_id) 순으로 결정적이다.
4. `record_turn` 하나가 한 트랜잭션이다. 잘못된 session ID·빈 해시·빈 질문은 ValueError다.
5. 실제 세션과 연결한다. `05_multiturn.py` 실행 전후로 각 턴의 근거를 기록하고, `sla-a-v2.md` 문장 하나를 수정해 `02_ingest.py`로 재적재한 뒤 stale 보고를 관찰한다. **실험 뒤 문서는 원복하고 재적재한다.** fingerprint가 바뀌어 새 target_uri로 적재되는 점도 설명한다.

필수 검증:

```bash
uv run python 12_refresh_challenge.py
```

공개 테스트에는 임시 DB에서의 재오픈·스코프 격리가 포함된다. 추가 테스트에는 실제 manifest 해시와의 대조, 갱신 후 원복까지의 시간순 기록을 포함한다.

배점: 영속 계약·공개 반례 12, 실제 세션 연결과 갱신 관찰 12, 트랜잭션·한계 설명 6.

## D. 통합 변경의 효과를 입증하기 — 20점

07/08과 A/B/C 중 자신이 연결한 변경을 09의 두 실행으로 비교하고, 13으로 짝 분석한다. 한 번에 한 가지 변경의 효과부터 본다.

- 09의 두 실행은 같은 `cases.jsonl`·`gold.jsonl`(provenance hash로 확인)과 같은 사례 유형을 쓴다. `CHANGED`에는 실제로 바꾼 변수만 선언한다. 선언하지 않은 변수가 바뀌면 분석기가 거절한다.
- bm25만 쓴 비교는 결정적이라 delta가 전부 0일 수 있다. 이는 "효과 없음"의 증거가 아니라 그 변형에 영향이 없다는 관찰이다. 분산 있는 변형(dense·rerank·자신의 합류 정책)으로 반복하거나, 답변 수준 비교로 보강한다.
- 검색 지표(recall@k)와 답변 사실성을 구분한다. 최소 4개의 답변을 `outputs/runs/<id>.json`의 인용과 gold 사실로 직접 대조하고, 달라진 답변의 원인이 검색인지 검증인지 설명한다.
- 실패 행·오류 행을 결과에서 제외하지 않고, 코드 상수 변경과 결과 폴더를 함께 제출한다.

`13_mini_pjt.py` 상단의 상수를 본인이 기록한 결과 경로로 바꾼다. delta는 **후보 − 기준선**이다. recall이 올라도 다른 유형에서 손실이 있으면 함께 보고한다. 1~3회 반복만으로 통계적 유의성을 주장하지 않는다.

배점: 실험 통제·짝 무결성 5, 검색·답변 지표 구분과 대조 5, 개선·악화 원인 설명 5, 한계·재현 조건 명시 5.

## 강사용 채점 메모

- 07: 문서명·URI를 hardcode한 정책은 새 고객·시점 사례로 구별한다. 범위 필터를 건너뛰고 RRF만 구현했는지, 미등록 ID 거절을 지웠는지 확인한다. `candidate_policy`가 입력에 없는 URI를 반환하면 프로덕션 코드가 ValueError로 막는다.
- 08: 인용을 통과시키려고 quote를 카드에 맞춰 바꾸는 역방향 검증은 거절한다. `numeric` 플래그를 끄거나 visual 근거로 수치를 통과시켰는지 본다. 검사 순서가 계약과 다르면 동순위 채점에서 감점한다.
- A: 날짜→문서 대응표를 hardcode한 구현은 겹침·미래 반례로 구별한다. 7/1 경계를 닫힌 구간으로 처리했는지, draft의 이유가 status로 나오는지 확인한다.
- B: `requires`를 비우고 관련도 정렬로만 해결했는지 본다. 표를 문장으로 미리 바꿔 제출하거나 렌더 비용에서 ID를 뺀 경우 거절한다. 예산이 묶음보다 1바이트 작을 때 부분 묶음을 반환하면 반례로 잡힌다.
- C: 메모리 dict 제출은 재시작 테스트에서 즉시 드러난다. 세션을 매 턴 새로 만들어 갱신을 회피했는지, 갱신 후 원문을 원복했는지 확인한다. 원문을 확인할 수 없는 인용의 처치(보수적 stale)를 구두로 묻는다.
- D: 가장 좋은 실행만 골랐는지, 실패 행을 지웠는지, gold/사례를 후보에게 유리하게 바꿨는지 확인한다(provenance hash로 검증). 검색 recall과 답변 사실성을 혼용하면 분석을 다시 요구한다.

공개 테스트는 계약 예시이며 실제 운영 코퍼스의 품질이나 분산 검색기의 통계적 특성을 인증하지 않는다. 학생이 추가한 통합 반례와 원문 대조 판정이 고급 과제 평가의 중심이다.
